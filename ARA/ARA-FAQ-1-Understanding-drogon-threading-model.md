# فهم نموذج خيوط التنفيذ في Drogon (Understanding Drogon's Threading Model)

Drogon هو إطار عمل سريع لتطبيقات الويب بلغة C++. وتعود سرعته الفائقة جزئياً إلى عدم إخفاء وتجريد نموذج خيوط التنفيذ البرمجية (Threading model) عن المطور. ومع ذلك، يتسبب هذا أيضاً في بعض اللبس، فمن الشائع رؤية تساؤلات ومناقشات حول سبب تأخر إرسال الاستجابات إلا بعد انتهاء بعض الاستدعاءات المانعة (Blocking calls)، أو لماذا يؤدي استدعاء دالة شبكية مانعة على حلقة الأحداث نفسها إلى حدوث حالة القفل المتبادل (Deadlock).. إلخ. تهدف هذه الصفحة إلى شرح الظروف الدقيقة التي تسبب هذه المشاكل وكيفية تجنبها.

## حلقات الأحداث وخيوط التنفيذ (Event loops and threads)

يعمل Drogon على مجمع خيوط تنفيذ (Thread pool)، حيث يمتلك كل خيط حلقة أحداث (Event loop) خاصة به. وتُعد حلقات الأحداث هي النواة الأساسية لإطار عمل Drogon. يحتوي كل تطبيق Drogon على حلقتي أحداث على الأقل: حلقة رئيسية (Main loop) وحلقة فرعية للمُعالجة (Worker loop). وتعمل الحلقة الرئيسية دائماً على خيط التنفيذ الرئيسي (الخيط الذي بدأ تنفيذ دالة `main`)، وهي المسؤولة عن إطلاق جميع حلقات المعالجة الفرعية. لنأخذ تطبيق "Hello World" كمثال، يقوم السطر `app().run()` ببدء حلقة الأحداث الرئيسية على خيط التنفيذ الرئيسي، والتي بدورها تنشئ 3 خيوط/حلقات معالجة فرعية:

```cpp
#include <drogon/drogon.h>
using namespace drogon;

int main()
{
    app().registerHandler("/", [](const HttpRequest& req
        , std::function<void (const HttpResponsePtr &)> &&callback) {
        auto resp = HttpResponse::newHttpResponse();
        resp->setBody("Hello world");
        callback(resp);
    });
    app().addListener("0.0.0.0", 8080);
    app().setNumThreads(3);
    app().run();
}
```

يبدو التسلسل الهرمي لخيوط التنفيذ كالتالي:

```text
            .-------------.
            | app().run() | <خيط التنفيذ الرئيسي>
            :-------------:
                  |
            .-----v------.
            | MAIN LOOP  |
            :------------:
                  | إنشاء وإطلاق (Spawns)
      .-----------+--------------.
      |           |              |
.-----v----.   .--v-------.  .---v----.
| Worker 1 |   | Worker 2 |  | إلخ...  |
:----------:   :----------:  :--------:
<خيط تنفيذ 1>  <خيط تنفيذ 2> <خيط تنفيذ...>
```

يعتمد عدد حلقات/خيوط المعالجة الفرعية على عدة متغيرات، تحديداً عدد الخيوط المحددة لخادم HTTP، وعدد اتصالات قواعد البيانات وNoSQL غير السريعة (Non-fast) التي يتم إنشاؤها — وسنتطرق للفرق بين الاتصالات السريعة وغير السريعة لاحقاً. فقط اعلم أن Drogon يمتلك خيوط تنفيذ أكثر من مجرد خيوط خادم HTTP. وتعمل كل حلقة أحداث بشكل أساسي كقائمة انتظار مهام (Task queue) توفر الوظائف التالية:

- قراءة المهام من قائمة الانتظار وتنفيذها. يمكنك إرسال مهام لتنفذ على حلقة أحداث من أي خيط آخر. عملية إرسال المهام خالية تماماً من القفل (Lock-free) بفضل هياكل البيانات الخالية من الأقفال، ولن تتسبب في تنافس البيانات (Data race) تحت أي ظرف. تعالج حلقات الأحداث المهام واحدة تلو الأخرى، وبالتالي تتمتع المهام بترتيب تنفيذ محدد بدقة. لكن هذا يعني أيضاً أن المهام التي تُدرج في القائمة بعد مهمة ضخمة وتستغرق وقتاً طويلاً سيتأخر تنفيذها.
- الاستماع إلى أحداث الشبكة التي تديرها وتوزيعها.
- تنفيذ المؤقتات الزمنية (Timers) عند انتهاء مهلتها (والتي ينشئها المستخدم عادة).

عندما لا يحدث أي مما سبق، تتوقف (Block) حلقة الأحداث/خيط التنفيذ وينتظر حدوثها.

```cpp
// إدراج مهمتين في قائمة انتظار حلقة الأحداث الرئيسية
trantor::EventLoop* loop = app().getLoop();
loop->queueInLoop([]{
    std::cout << "task1: سأنتظر لمدة 5 ثوانٍ\n";
    std::this_thread::sleep_for(5s);
    std::cout << "task1: أهلاً!\n";
});
loop->queueInLoop([]{
    std::cout << "task2: مرحباً بالعالم!\n";
});
```

من الواضح الآن لماذا يؤدي تشغيل الكود أعلاه إلى ظهور عبارة `task1: سأنتظر لمدة 5 ثوانٍ` فوراً، ثم يتوقف لمدة 5 ثوانٍ، وبعدها يظهر كل من `task1: أهلاً!` و `task2: مرحباً بالعالم!` معاً.

> **النصيحة الأولى:** لا تقم بطلب عمليات إدخال/إخراج حاجبة (Blocking IO) داخل حلقة الأحداث، لأن بقية المهام الأخرى ستضطر للانتظار حتى تنتهي عملية الإدخال/الإخراج تلك.

## عمليات الإدخال/الإخراج الشبكية في الممارسة العملية (Network IO in practice)

يرتبط كل شيء تقريباً في Drogon بحلقة أحداث معينة، ويشمل ذلك تدفقات/اتصالات TCP، وعملاء HTTP، وعملاء قواعد البيانات، والذاكرة المؤقتة للبيانات. ولتجنب ظروف التنافس (Race conditions)، تُنفذ جميع عمليات الإدخال/الإخراج داخل حلقة الأحداث المرتبطة بها. إذا تم استدعاء عملية إدخال/إخراج من خيط تنفيذ آخر، يتم تخزين المعاملات وإرسالها كمهمة إلى حلقة الأحداث المناسبة. لهذا الأمر بعض الآثار، على سبيل المثال، عند استدعاء واجهة برمجية بعيدة من داخل معالج HTTP أو إجراء استعلام قاعدة بيانات، فإن دالة الاستدعاء العكسي (Callback) القادمة من العميل قد لا تنفذ بالضرورة (وفي الواقع، غالباً لا تنفذ) على خيط التنفيذ نفسه الذي يعمل عليه المعالج.

```cpp
app().registerHandler("/send_req", [](const HttpRequest& req
    , std::function<void (const HttpResponsePtr &)> &&callback) {
    // سيعمل هذا المعالج على أحد خيوط تنفيذ خادم HTTP

    // إنشاء عميل HTTP يعمل على حلقة الأحداث الرئيسية
    auto client = HttpClient::newHttpClient("https://drogon.org", app().getLoop());
    auto request = HttpRequest::newHttpRequest();
    client->sendRequest(request, [](ReqResult result, const HttpResponse& resp) {
        // تعمل دالة الاستدعاء العكسي هذه على خيط التنفيذ الرئيسي
    });
});
```

لذلك، من الممكن أن تتسبب في سد وإعاقة حلقة الأحداث إذا لم تكن مدركاً لما يفعله كودك في الواقع، مثل إنشاء عدد ضخم من عملاء HTTP على حلقة الأحداث الرئيسية وإرسال جميع الطلبات الخارجية، أو تشغيل دوال تتطلب معالجة حسابية كثيفة داخل دالة استدعاء عكسي لقاعدة بيانات، مما يمنع معالجة استعلامات قاعدة البيانات الأخرى.

```text
 Worker 1       Main Loop        Worker2
.---------.    .----------.     .---------.
|         |    |          |     |         |
| req 1-. |    |----------|  .--+--req 2  |
|       :-+----+->        |  |  |         |
|         |    | send http|  |  |---------|
|---------| a.-|   req 1  |  |  |         |
|other req| s| |----------|  |  |         |
|---------| y| |      <---+--:  |         |
|         | n| |send http |     |         |
|         | c| |  req 2   |-.   |         |
|         |  | |----------| |a  |---------|
|         |  | |http resp1| |s  |other req|
|         |  :-|>compute  | |y  |---------|
|         |    |          | |n  |         |
|         | .--+-generate | |c  |         |
|         | |  | response | |   |         |
|         | |  |----------| |   |         |
|         | |  |http resp2|<:   |         |
|---------| |  | compute  |     |---------|
|response<|-:  |          |-----|>        |
|send back|    | generate |     |send resp|
|         |    | response |     | back    |
:---------:    :----------:     :---------:
```

ينطبق المبدأ نفسه على خادم HTTP أيضاً إذا تم إنشاء استجابة من خيط تنفيذ منفصل (مثلاً: داخل دالة استدعاء عكسي لقاعدة بيانات)، فسيتم إدراج الاستجابة في قائمة انتظار خيط التنفيذ المرتبط بها لإرسالها بدلاً من إرسالها فوراً.

> **النصيحة الثانية:** كن واعياً لأماكن وضع عملياتك الحسابية، حيث يمكنها أن تضر بمعدل الإنتاجية (Throughput) إذا لم تكن حذراً.

## حدوث القفل المتبادل في حلقة الأحداث (Deadlocking the event loop)

مع فهم كيفية تصميم Drogon، لن يكون من الصعب إدراك كيفية التسبب في قفل متبادل (Deadlock) لحلقة الأحداث، فكل ما عليك هو إرسال طلب إدخال/إخراج بعيد والانتظار لحين اكتماله على حلقة الأحداث نفسها — الواجهات المتزامنة (Sync API) تفعل ذلك تماماً، حيث ترسل طلب إدخال/إخراج وتنتظر استجابة دالة الاستدعاء العكسي.

```cpp
app().registerHandler("/dead_lock", [](const HttpRequest& req
    , std::function<void (const HttpResponsePtr &)> &&callback) {
    auto currentLoop = app().getIOLoops()[app().getCurrentThreadIndex()];
    auto client = HttpClient::newHttpClient("https://drogon.org", currentLoop);
    auto request = HttpRequest::newHttpRequest();
    auto resp = client->sendRequest(resp); // قفل متبادل! استدعاء واجهة متزامنة (DEADLOCK)
});
```

ويمكن توضيح ذلك بصرياً كالتالي:

```text
     حلقة أحداث ما
   .------------.
   | new client |
   | new request|
   |send request|
 .->WAIT resp---+-.
 | |  ....      | |
?| |            | |
?| |------------| |
?| |            | |
?| |            | |
?| |            | |
?| |            | |
 | |            | |
 | |            | |
 | |            | |
 | |            | |
 | |            | |
 | |            | |
 | |------------| |
 | | read resp  | |
 :-+-         <-+-:
   | عذراً      |
   | deadlock   |
   :------------:
```

وينطبق الشيء نفسه على كل شيء آخر مثل قواعد البيانات، استدعاءات NoSQL، وغيرها. لحسن الحظ، تعمل اتصالات قواعد البيانات غير السريعة (Non-fast DB clients) على خيوط تنفيذ خاصة بها، حيث يحصل كل عميل على خيطه الخاص. لذلك من الآمن إجراء استعلامات متزامنة لقواعد البيانات من معالج HTTP. ومع ذلك، يجب عليك عدم تشغيل استعلامات متزامنة لقاعدة البيانات داخل دالة الاستدعاء العكسي للعميل نفسه، وإلا فسيحدث الشيء نفسه.

> **النصيحة الثالثة:** الواجهات المتزامنة (Sync APIs) ضارة بالصحة البرمجية لكل من الأداء والسلامة. تجنبها كالأوبئة. وإذا كان عليك استخدامها، فتأكد من تشغيل العميل على خيط تنفيذ منفصل.

### اتصالات قواعد البيانات السريعة (Fast DB clients)

صُمم Drogon ليركز على الأداء أولاً وسهولة الاستخدام ثانياً. اتصالات قواعد البيانات السريعة هي اتصالات تتشارك خيوط التنفيذ مع خادم HTTP نفسه. وتعمل هذه الميزة على تحسين الأداء عن طريق القضاء على الحاجة لإرسال الطلبات إلى خيط تنفيذ آخر وتجنب تبديل السياق (Context switch) بواسطة نظام التشغيل. ولكن بسبب هذه الحقيقة، لا يمكنك إجراء استعلامات متزامنة عليها وإلا ستتسبب في قفل متبادل لحلقة الأحداث.

## الروتينات الفرعية المشتركة هي الحل (Coroutines to the rescue)

كانت المعضلة في تطوير واستخدام Drogon هي أن الواجهات اللامتزامنة أكثر كفاءة ولكنها مزعجة في الاستخدام، بينما الواجهات المتزامنة قد تسبب مشاكل وبطيئة ولكن البرمجة بها أسهل بكثير. يمكن أن تكون إعلانات تعبيرات لامبدا طويلة ومملة، والتراكيب اللغوية ليست ممتعة في القراءة. بالإضافة إلى ذلك، لا يعمل الكود من الأعلى إلى الأسفل، بل مليء بالاستدعاءات العكسية. الواجهات المتزامنة أنظف بكثير من اللامتزامنة، ولكن على حساب الأداء.

```cpp
// واجهة قواعد البيانات اللامتزامنة في Drogon
auto db = app().getDbClient();
db->execSqlAsync("INSERT......", [db, callback](auto result){
    db->execSqlAsync("UPDATE .......", [callback](auto result){
        // معالجة النجاح
    },
    [callback](const DbException& e) {
        // معالجة الفشل
    })
},
[callback](const DbException& e){
    // معالجة الفشل
})
```

مقارنة بـ:

```cpp
// واجهة Drogon المتزامنة (يمكن معالجة الاستثناءات تلقائياً بواسطة إطار العمل)
db->execSqlSync("INSERT.....");
db->execSqlSync("UPDATE.....");
```

لا بد من وجود طريقة للجمع بين الميزتين، أليس كذلك؟ هنا يأتي دور الروتينات الفرعية المشتركة (Coroutines) في C++20، فهي غلاف مدعوم من المجمع حول الاستدعاءات العكسية ليجعل كودك يبدو وكأنه متزامن، ولكنه لامتزامن بالكامل في الواقع. إليك الكود نفسه باستخدام الروتينات الفرعية المشتركة:

```cpp
co_await db->execSqlCoro("INSERT.....");
co_await db->execSqlCoro("UPDATE.....");
```

إنه يتطابق تماماً مع الواجهة المتزامنة، ولكنه أفضل بكثير في كل جانب تقريباً، حيث تحصل على جميع فوائد الأداء اللامتزامن مع الاستمرار في استخدام واجهة بسيطة تشبه المتزامنة. يحث المطورون على استخدام الروتينات الفرعية المشتركة عندما تستطيع (GCC >= 11, MSVC >= 16.25). ومع ذلك، فهي ليست سحراً مطلقاً، فهي لن تحل مشاكل انسداد حلقات الأحداث وتنافس البيانات نيابة عنك، لكن من السهل تنقيح وتفهم الكود اللامتزامن باستخدامها.

> **النصيحة الرابعة:** استخدم الروتينات الفرعية المشتركة (Coroutines) عندما تكون متاحة لديك.

## ملخص (Summary)

- استخدم روتينات C++20 الفرعية المشتركة واتصالات قواعد البيانات السريعة (`Fast DB`) عندما يكون ذلك ممكناً.
- يمكن للواجهات المتزامنة أن تبطئ حلقة الأحداث أو تسبب قفلاً متبادلاً (Deadlock).
- إذا كان عليك استخدام واجهة متزامنة، فتأكد من أنها مرتبطة بخيط تنفيذ منفصل.
