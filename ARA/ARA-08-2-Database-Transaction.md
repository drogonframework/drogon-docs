# قاعدة البيانات (Database) - المعاملات (Transactions)

> **المعاملات (Transactions)** هي ميزة مهمة في قواعد البيانات العلائقية، ويوفر Drogon دعماً للمعاملات عبر الفئة `Transaction`.

تُنشأ كائنات الفئة `Transaction` بواسطة `DbClient`، وتُنفذ العديد من العمليات المتعلقة بالمعاملات تلقائياً:

- في بداية إنشاء كائن `Transaction`، يُنفذ أمر البدء (begin statement) تلقائياً لبدء المعاملة.
- عند تدمير كائن `Transaction` (Destruction)، يُنفذ أمر التطبيق (commit statement) تلقائياً لإنهاء المعاملة وتأكيدها.
- في حال حدوث استثناء يتسبب في فشل المعاملة، يُنفذ أمر التراجع (rollback statement) تلقائياً للتراجع عن المعاملة.
- إذا تم التراجع عن المعاملة، فستعيد جملة SQL استثناءً (إما بإطلاق استثناء Throw exception أو عبر دالة الاستدعاء اللاحق للاستثناءات Exception callback).

### إنشاء المعاملة (Transaction Creation)

يوفر `DbClient` طريقة إنشاء المعاملة كالتالي:

```c++
std::shared_ptr<Transaction> newTransaction(const std::function<void(bool)> &commitCallback = std::function<void(bool)>())
```

هذه الواجهة بسيطة جداً، حيث تُعيد مؤشراً ذكياً (Smart pointer) لكائن `Transaction`. ومن الواضح أنه عندما يفقد المؤشر الذكي جميع محتفظيه ويُدمر كائن المعاملة، تنتهي المعاملة. يُستخدم المعامل `commitCallback` لإعادة النتيجة عما إذا كان تأكيد المعاملة (Commit) قد نجح أم لا. وتجدر الإشارة إلى أن دالة الاستدعاء اللاحق هذه تُستخدم فقط لبيان ما إذا كان أمر `commit` قد نجح أم لا. أما إذا تم التراجع عن المعاملة تلقائياً أو يدوياً أثناء التنفيذ، فلن تُنفذ دالة الاستدعاء اللاحق `commitCallback`. وبشكل عام ينجح أمر `commit` وتكون قيمة المعامل المنطقي (bool parameter) لهذه الدالة هي `true`. فقط في بعض الحالات الخاصة مثل انقطاع الاتصال أثناء عملية التأكيد، ستشعر دالة `commitCallback` المطور بفشل التأكيد، وفي هذه الحالة تكون حالة المعاملة على الخادم غير مؤكدة، ويحتاج المطور للتعامل مع هذه الحالة بشكل خاص. بالطبع، ونظراً لأن هذه الحالة نادرة الحدوث، يمكن للمطور في الخدمات غير الحساسة اختيار التغاضي عن هذا الحدث عبر التغاضي عن المعامل `commitCallback` عند إنشاء المعاملة (حيث يُمرر الاستدعاء الفارغ الافتراضي إلى الدالة newTransaction).

تتطلب المعاملة الاحتكار التام لاتصال قاعدة البيانات. لذلك أثناء إنشاء المعاملة، يحتاج `DbClient` إلى اختيار اتصال خالي من مجموعة الاتصالات (Connection pool) الخاصة به وتسليمه لإدارة كائن المعاملة. وينتج عن ذلك إشكال محتمل: إذا كانت جميع الاتصالات في `DbClient` تنفذ جمل SQL أو معاملات أخرى، فستُعطل الواجهة خيط التنفيذ حتى يتوفر اتصال خالي.

يوفر إطار العمل أيضاً واجهة لامتزامنة لإنشاء المعاملات كالتالي:

```c++
void newTransactionAsync(const std::function<void(const std::shared_ptr<Transaction> &)> &callback);
```

تُعيد هذه الواجهة كائن المعاملة عبر دالة الاستدعاء اللاحق، ولا تُعطل خيط التنفيذ الحالي، مما يضمن التزامن الفائق للتطبيق. ويمكن للمطورين استخدامها أو استخدام النسخة المتزامنة وفقاً للحاجة الفعلية.

### واجهة المعاملة (Transaction Interface)

تطابق واجهة `Transaction` تقريباً واجهة `DbClient`، باستثناء الاختلافين التاليين:

- توفر `Transaction` واجهة `rollback()` التي تتيح للمطور التراجع عن المعاملة تحت أي ظرف. وفي بعض الأحيان تكون المعاملة قد تم التراجع عنها تلقائياً بالفعل، وحينها لن يكون لاستدعاء الواجهة `rollback()` أي أثر سلبي، لذا يُعد الاستخدام الصريح لواجهة `rollback()` استراتيجية جيدة على الأقل لضمان عدم تأكيد المعاملة بالخطأ.
- لا يمكن للمطور استدعاء واجهة `newTransaction()` الخاصة بالمعاملة نفسها، وهو أمر بديهي. ورغم أن قواعد البيانات تمتلك مفهوم المعاملات الفرعية (Sub-transactions)، إلا أن إطار العمل لا يدعمها حالياً.

في الواقع، تم تصميم `Transaction` كفئة فرعية (Subclass) من `DbClient` للحفاظ على اتساق هذه الواجهات، وفي الوقت نفسه يوفر ذلك ظروفاً مريحة لاستخدام [تخطيط الكائنات العلائقية (ORM)](/ARA/ARA-08-3-Database-ORM).

ولا يوفر إطار العمل حالياً واجهة للتحكم في مستويات عزل المعاملات (Transaction isolation levels)، أي أن مستوى العزل يكون هو المستوى الافتراضي لخدمة قاعدة البيانات الحالية.

### دورة حياة المعاملة (Transaction Life Cycle)

يُحتفظ بالمؤشر الذكي لكائن المعاملة بواسطة المطور. وعندما تكون هناك جمل SQL لم تُنفذ بعد، سيحتفظ بها إطار العمل، فلا داعي للقلق بشأن تدمير كائن المعاملة في حال وجود جمل SQL قيد التنفيذ. بالإضافة إلى ذلك، غالباً ما يُلتقط المؤشر الذكي لكائن المعاملة ويُستخدم داخل دالة الاستدعاء اللاحق للنتيجة لإحدى واجهاتها. وهذه هي الطريقة الطبيعية للاستخدام، فلا داعي للقلق من أن يتسبب المرجع الدائري (Circular reference) في عدم تدمير كائن المعاملة إطلاقاً، لأن إطار العمل يساعد المطور في كسر المرجع الدائري تلقائياً.

### مثال توضيحي (One Example)

لأبسط مثال، لنفرض وجود جدول مهام يختار منه المطور مهمة غير معالجة ويغير حالتها إلى قيد المعالجة. ولتجنب شروط السباق للتزامن (Concurrent race conditions)، نستخدم الفئة `Transaction`، ويكون البرنامج كالتالي:

```c++
{
    auto transPtr = clientPtr->newTransaction();
    transPtr->execSqlAsync( "select * from tasks where status=$1 for update order by time",
                            "none",
                            [=](const Result &r) {
                                if (r.size() > 0)
                                {
                                    std::cout << "Got a task!" << std::endl;
                                    *transPtr << "update tasks set status=$1 where task_id=$2"
                                              << "handling"
                                              << r[0]["task_id"].as<int64_t>()
                                              >> [](const Result &r)
                                                 {
                                                    std::cout << "Updated!";
                                                    ... do something about the task;
                                                 }
                                              >> [](const DrogonDbException &e)
                                                 {
                                                    std::cerr << "err:" << e.base().what() << std::end;
                                                 };
                                }
                                else
                                {
                                    std::cout << "No new tasks found!" << std::endl;
                                }
                            },
                            [](const DrogonDbException &e) {
                                std::cerr << "err:" << e.base().what() << std::end;
                            });
}
```

في هذه الحالة، يُستخدم `select for update` لتجنب التعديلات المتزامنة. وتكتمل جملة التحديث `update` داخل دالة الاستدعاء اللاحق لنتيجة جملة `select`. وتُستخدم الأقواس المزخرفة الخارجية للحد من نطاق `transPtr` ليتسنى تدميره في الوقت المناسب بعد إتمام تنفيذ SQL لإنهاء المعاملة.
