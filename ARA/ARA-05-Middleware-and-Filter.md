# البرمجيات الوسيطة والفلاتر (Middleware and Filter)

في [مثال](/ARA/ARA-04-2-Controller-HttpController) المتحكم HttpController، ينبغي للدالة getInfo التحقق مما إذا كان المستخدم قد قام بتسجيل الدخول أم لا قبل إرجاع معلومات المستخدم. يمكننا كتابة هذا المنطق داخل الدالة getInfo نفسها، ولكن من الواضح أن التحقق من حالة تسجيل دخول المستخدم يمثل منطقاً عاماً سُتستخدمه واجهات عديدة، لذا ينبغي استخلاصه بشكل منفصل وإعداده ليعمل قبل استدعاء المعالج (Handler)، وهو تماماً ما تقوم به الفلاتر (Filters).

تعتمد البرمجيات الوسيطة (Middleware) في Drogon على نموذج البصلة (Onion model). فبعد أن يكمل إطار العمل مطابقة مسار URL، يقوم بالتتابع باستدعاء البرمجيات الوسيطة المسجلة لذك المسار. وداخل كل برمجية وسيطة، يمكن للمستخدمين اختيار اعتراض الطلب (Intercept) أو تمريره (Pass through)، مع إضافة منطق المعالجة المسبقة (Pre-processing) والمعالجة اللاحقة (Post-processing).

إذا قامت برمجية وسيطة باعتراض الطلب، فلن يستمر الطلب للوصول إلى الطبقات الداخلية للبصلة، ولن يتم استدعاء المعالج المناظر. ومع ذلك، فسوف يمر الطلب عبر منطق المعالجة اللاحقة للبرمجيات الوسيطة (Middleware) في الطبقات الخارجية.

في الواقع، تُعتبر الفلاتر برمجيات وسيطة تُسقط عمليات المعالجة اللاحقة. ويمكن استخدام البرمجيات الوسيطة والفلاتر معاً جنباً إلى جنب عند تسجيل المسارات.

### البرمجيات الوسيطة والفلاتر المدمجة (Built-in Middleware/Filter)

يتضمن Drogon الفلاتر الشائعة التالية:

- `drogon::IntranetIpFilter`: يسمح فقط بطلبات HTTP القادمة من عناوين IP الخاصة يشبكة الإنترانت / الشبكة الداخلية (Intranet IP)، أو يعيد صفحة الخطأ 404.
- `drogon::LocalHostFilter`: يسمح فقط بطلبات HTTP القادمة من 127.0.0.1 أو ::1، أو يعيد صفحة الخطأ 404.

### البرمجيات الوسيطة والفلاتر المخصصة (Custom Middleware/Filter)

- #### تعريف البرمجيات الوسيطة (Middleware Definition)

  يمكن للمستخدمين تخصيص البرمجيات الوسيطة. حيث يلزمك الوراثة من قالب الفئة `HttpMiddleware`، ويكون نوع القالب هو نوع الفئة الفرعية نفسها. على سبيل المثال، إذا أردت تفعيل دعم مشاركة الموارد عبر الأصول المختلفة (CORS) لبعض المسارات، يمكنك تعريفها كالتالي:

  ```c++
  class MyMiddleware : public HttpMiddleware<MyMiddleware>
  {
  public:
      MyMiddleware(){};  // لا تنسى دالة الإنشاء (Constructor)

      void invoke(const HttpRequestPtr &req,
                  MiddlewareNextCallback &&nextCb,
                  MiddlewareCallback &&mcb) override
      {
          const std::string &origin = req->getHeader("origin");
          if (origin.find("www.some-evil-place.com") != std::string::npos)
          {
              // اعتراض الطلب مباشرة
              mcb(HttpResponse::newNotFoundResponse(req));
              return;
          }
          // القيام بعمل ما قبل استدعاء البرمجية الوسيطة التالية
          nextCb([mcb = std::move(mcb)](const HttpResponsePtr &resp) {
              // القيام بعمل ما بعد عودة البرمجية الوسيطة التالية
              resp->addHeader("Access-Control-Allow-Origin", origin);
              resp->addHeader("Access-Control-Allow-Credentials","true");
              mcb(resp);
          });
      }
  };
  ```

  يلزمك إستبدال/تجاوز (override) الدالة الوهمية `invoke` للفئة الأب لتنفيذ منطق الفلتر.

  تحتوي هذه الدالة الوهمية على ثلاثة معاملات، وهي:

  - **req**: طلب HTTP.
  * **nextCb**: دالة الاستدعاء اللاحق (Callback function) للدخول إلى الطبقة الداخلية التالية للبصلة. واستدعاء هذه الدالة يعني استدعاء البرمجية الوسيطة التالية أو المعالج النهائي. عند استدعاء nextCb، فإنها تقبل دالة أخرى كمعامل. وتُستدعى هذه الدالة عند العودة من الطبقات الداخلية، ويُمرر `HttpResponsePtr` العائد من الطبقات الداخلية كمعامل لهذه الدالة.
  * **mcb**: دالة الاستدعاء اللاحق (Callback function) للعودة إلى الطبقة الأعلى للبصلة. واستدعاء هذه الدالة يعني العودة إلى الطبقة الخارجية للبصلة. وفي حال تجاوز nextCb واستدعاء mcb فقط، فإن ذلك يعني اعتراض الطلب والعودة مباشرة إلى الطبقة الأعلى.

- #### تعريف الفلاتر (Filter Definition)

  بالطبع يمكن للمستخدمين تخصيص الفلاتر، حيث يلزمك الوراثة من قالب الفئة `HttpFilter`، ويكون نوع القالب هو نوع الفئة الفرعية نفسها. على سبيل المثال، إذا أردت إنشاء `LoginFilter`، يمكنك تعريفه كالتالي:

  ```c++
  class LoginFilter:public drogon::HttpFilter<LoginFilter>
  {
  public:
      void doFilter(const HttpRequestPtr &req,
                    FilterCallback &&fcb,
                    FilterChainCallback &&fccb) override ;
  };
  ```

  يمكنك إنشاء الفلاتر عبر الأمر `drogon_ctl`، راجع دليل [drogon_ctl](/ARA/ARA-12-drogon_ctl-Command?id=filter-creation).

  يلزمك إستبدال/تجاوز (override) الدالة الوهمية `doFilter` للفئة الأب لتنفيذ منطق الفلتر.

  تحتوي هذه الدالة الوهمية على ثلاثة معاملات، وهي:

  - **req**: طلب HTTP.
  - **fcb**: دالة الاستدعاء اللاحق للفلتر (Filter callback function)، ونوع الدالة هو `void (HttpResponsePtr)`. عندما يحدد الفلتر أن الطلب غير صالح، يتم إرجاع الاستجابة المحددة إلى المتصفح عبر هذه الدالة.
  - **fccb**: دالة الاستدعاء اللاحق لسلسلة الفلاتر (Filter chain callback function)، ونوع الدالة هو `void ()`. عندما يحدد الفلتر أن الطلب صالح، فإنه يخبر Drogon باستدعاء الفلتر التالي أو المعالج النهائي عبر هذه الدالة.

  يمكن الرجوع في التنفيذ التفصيلي إلى طريقة تنفيذ الفلاتر المدمجة في Drogon.

- #### تسجيل البرمجيات الوسيطة والفلاتر (Middleware/Filter Registration)

  يصاحب تسجيل البرمجيات الوسيطة والفلاتر دائماً تسجيل المتحكمات. حيث يمكن الماكروهات (مثل PATH_ADD و METHOD_ADD وغيرها) المذكورة سابقاً إضافة اسم برمجية وسيطة واحدة أو أكثر أو فلاتر في نهاية السطر. على سبيل المثال، نقوم بتغيير سطر التسجيل للدالة `getInfo` السابقة إلى الشكل التالي:

  ```c++
  METHOD_ADD(User::getInfo,"/{1}/info?token={2}",Get,"LoginFilter","MyMiddleware");
  ```

  بعد مطابقة المسار بنجاح، لن يتم استدعاء الدالة `getInfo` إلا عند تحقق الشرطين التاليين:

  1. يجب أن يكون الطلب طلب HTTP من نوع Get.
  2. يجب أن يكون الطرف الطالب قد قام بتسجيل الدخول بالفعل.

  كما ترى، يُعد إعداد وتسجيل البرمجيات الوسيطة والفلاتر أمراً بسيطاً للغاية. ولا يحتاج ملف المتحكم (Controller) الذي يسجل برمجيات وسيطة إلى تضمين ملف الترويسة الخاص بتلك البرمجيات الوسيطة. توجد حالة من الفصل التام بين البرمجيات الوسيطة (middleware) ووحدة التحكم (controller).

  > **ملاحظة: إذا كانت البرمجية الوسيطة أو الفلتر معرفة داخل نطاق أسماء (Namespace)، فيجب كتابة نطاق الأسماء كاملاً عند التسجيل.**
